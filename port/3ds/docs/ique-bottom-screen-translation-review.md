# iQue 3DS 下屏内嵌英文文案校对表

本表只列源码中写死、由 3DS 下屏 UI 自己绘制的英文文案，以及下屏显示的区域/伙伴名、ROM 错误提示和触控菜单固定标题。**不包含**之前已经修复为读取 iQue 游戏消息并保留中文字形编号的敌人名、道具名、战斗指令等动态游戏文本。

完整逐条清单在同目录的 `ique-bottom-screen-translation-review.csv`，Windows Excel 可直接打开（UTF-8 BOM）。本版列出 230 条去重后的源码内嵌文案/名称。当前中文是首轮建议，所有带“暂译/待校对”的角色名、地名、玩法术语请你修改或确认。程序尚未使用这些译文。

## 实施建议：不要把 UTF-8 直接交给目前的字体函数

目前 `bottom_screen.c` 的主文字渲染器不是通用 Unicode 字体：英文走游戏字体的 ASCII 槽；上一轮下屏中文修复使用私用区字符 U+E000 + iQue 字形编号，`cjk_slot()` 再从 `charset_standard_OFFSET` 读取 16×16 字形。动态消息转换器 `touch_menu.c` 能从 iQue 原生双字节编码计算字形编号，但这不等于存在完整的“Unicode 汉字 → iQue 字形号”表。把普通中文 UTF-8 直接放进 C 字符串会得到乱码或空白。

推荐分两步：

1. **先维护 UTF-8 中文文案目录**（本表校对完成后作为唯一源文件），不要手工写难以维护的十六进制字节。
2. **构建时做字形映射转换**：建立校对过的“汉字 Unicode → iQue 字形编号”表，再将每句中文转成渲染器当前使用的 U+E000+编号序列，生成 C 头文件；在 CI 中检查每个汉字都有映射，映射缺失时直接报错，避免静默显示方块。字形编号必须来自 iQue 文本数据/真实字库对应关系，而不是按 Unicode 码位猜测。

### iQue 编码还是独立字体？

- **沿用 iQue 字库（建议优先）**：体积小、与游戏字体风格一致，也复用现有 CJK 字形缓存。缺点是必须建立可靠的 Unicode 到原版字形编号映射；神游文本用的双字节序列是游戏内部编码，不应默认当成 UTF-8、GBK 或 GB2312。
- **独立中文字体子集**：用授权允许再分发的中文字体，只把最终译文需要的汉字栅格化为 16×16 或 14×14 图集，随程序嵌入。这样无需研究 iQue 的字形编号，UTF-8 也可直接检索；代价是新增字体资源/许可文件、图集映射和字重/基线调校，视觉上与原版字库可能不完全一致。

**我的建议是先走 iQue 字库路线**：先从 ROM 原生消息数据建立并验证映射（同一个编码在游戏原文中出现时应与上下文一致），然后把经过确认的中文菜单词条转为私用区字形 token。若某些汉字在原版字库中不存在，才对这些缺字做小型补字图集；不必一开始替换整套字体。

### 绘制入口要一起统一

主字号的 `text()` / `text_width()` 已理解上一轮使用的 CJK 私用区 token；但提示/加载/随机模式的一部分文字走 `small_text()` / `small_text_center()`，它们目前逐字节遍历并只画 8×8 ASCII 控制台字体。翻译接入时需要同时处理这些小字号入口：遇到 CJK token 时用主字体按缩放绘制，或统一让菜单 UI 走同一个 UTF-8-aware 的布局/绘制函数。否则会出现部分页面能显示中文、部分页面仍空白的问题。

## 交付/打包注意

`.3dsx` 与 `.cia` 的 RomFS 中仍需要内嵌 `romdata_ique.bin` 这张运行时映射表，因为 `pm3ds_rom.c` 会通过 `romfs:/romdata_ique.bin` 读取它。发布 ZIP 可以不把它作为独立文件交付；但不能从两个可执行包的内部彻底移除，除非另行修改运行时读取机制。
